# 08. 운영

**결론: 한 사람이 주 3시간 안에 운영할 수 있어야 한다. 사람이 행동하지 않을 경보는 만들지 않는다.**

## 1. 관측성

모든 기록은 `trace_id`, `task_id`, `role_id`, `harness`, `model`, `base_sha`, `policy_hash`, `vault_version`을 가진다. 프롬프트 본문은 기본으로 남기지 않는다.

| 지표 | 경보 | 행동 |
|---|---|---|
| `ax_hook_fail_open_total` | 1건 | 해당 세션 종료, 1시간 2건이면 `ax freeze` |
| `ax_policy_deny_total` | 10분 20건 | 작업 중지, 인젝션 확인 |
| `ax_budget_ratio` | 0.8, 0.95 | [02](02-orchestration.md) §6 예산 정책 확인 |
| `ax_approval_pending_age` | 만료 25% 전 | 1회 알림 |
| `ax_backup_age_hours` | 26 초과 | 백업 재실행 |
| `ax_outbox_oldest_seconds` | 600 초과 | 외부 서비스 확인 |
| `service_slo_burn` | 빠른 소진 | 되돌리기 검토 |

SEV1만 밤에 알린다. 나머지는 하루 한 번 묶는다. 서비스는 외부 가용성 감시를 둔다. AX 머신은 꺼질 수 있으므로 26시간 넘게 백업 신호가 없을 때만 알린다.

## 2. 서비스 목표

| 대상 | 목표 |
|---|---|
| 개별 서비스 | 매니페스트의 `objectives`. 기본 제안은 월 가용성 99.5% |
| 결제 능력 사용 시 | 결제 이벤트 99%를 5분 안에 처리 |
| AX | SLO 없음. 멈춰도 서비스는 계속 동작 |

1인 운영에서 상시 대응이 어려우므로 99.9%를 약속하지 않는다.

## 3. KPI

| KPI | 계산 | 반대 지표 |
|---|---|---|
| 흐름 시간 | `define` 승인부터 `release` 통과까지의 중앙값. 유형별로 나눔 | 30일 내 SEV1·2 |
| 표준 준수 | 매니페스트와 적합성 검사를 통과한 서비스 / 운영 서비스 | 예외 승인 수 |
| 갱신 지연 | 현재 또는 직전 주 버전을 쓰는 서비스 비율 | 갱신 뒤 되돌림 |
| 지식 이전 | 다른 서비스에서 온 활성 지식이 쓰인 작업 / 전체 작업 | 강등률 |
| 서비스 비용 | (정산된 LLM + 인프라 + 외부 도구) / 활성 서비스 | 창업자 시간 |
| 결제·보안 장애 | SEV1·2 건수 / 배포 100건 | 탐지까지 걸린 시간 |
| 재사용 효과 | 90일 내 3회 이상 쓰인 활성 자산 / 활성 자산 | 강등률, 주입 토큰 |
| 검토 부담 | 병합 1건당 창업자 분 | 병합 후 결함률 |
| 기업 기능 시간 | 확정한 주간 분 / 상한 | 놓친 기한 |
| 예상 정확도 | 실제 확인 시간 / 예상 시간의 중앙값 | 검토 부담 |
| 자율 완료 | 개입 없이 게이트를 통과한 작업 / 시작한 작업 | 게이트 우회 |

지표는 [15](15-founder-console.md) §6의 대시보드에 보인다. 실제 서비스 전에는 기준 서비스로 재고 실적과 섞지 않는다. 각 지표는 첫 4주에 기준선만 잰다. 그 뒤 목표를 정한다. 구독 비용은 실제 청구액을 사용 시간 비율로 나누고 배분값임을 표시한다.

## 4. 백업

| 대상 | RPO | RTO | 방법 |
|---|---|---|---|
| `state.db` | 1시간 | 2시간 | SQLite 백업 API, 암호화 |
| 볼트·아티팩트 | 24시간 | 4시간 | 버전별 암호화 복사 |
| 서비스 DB | 공급자 PITR 확인 후 확정 | 4시간 | PITR + 별도 논리 백업 |
| 코드·정책 | 푸시 시점 | 1시간 | GitHub + 주간 미러 |
| 복구 키 | - | - | 오프라인 2곳 |

WAL 중인 DB 파일을 그냥 복사하지 않는다. 백업 계정은 추가만 가능하고 삭제할 수 없다.
월 1회 빈 환경에 복원한다. 무결성, 이벤트 사슬, 삭제 표식, 볼트 링크, 승인 폐기 상태를 검사한다.
복원 뒤에는 모든 미소비 승인을 폐기한다. 백업 시점 이후 소비된 승인이 다시 쓰일 수 있기 때문이다.
WSL은 유휴 상태에서 꺼질 수 있다. 예약 작업은 놓친 실행을 시작 때 한 번 보충한다(`Persistent=true`).
RPO는 AX가 실행 중인 시간에만 적용한다.
WSL의 가상 디스크 안 복사본은 백업으로 세지 않는다.

## 5. 런북

| 상황 | 절차 |
|---|---|
| 비밀 노출 | freeze → 키 폐기 → 사용 로그 → 삭제 → 새 키 → 재발 시험 |
| 배포 장애 | 새 배포 중지 → 이전 산출물 → DB 호환 확인 → 사용자 공지 초안 |
| 결제 불일치 | 권리 유지 → 공급자 조회 → 대사 보고 → 승인 후 보정 |
| 볼트 오염 | freeze → `ax memory rollback` → 해당 증거 격리 → 영향 작업 조회 |
| DB 손상 | 쓰기 중지 → 원본 보존 → 최근 백업 → 원격 상태와 대조 |
| 모델 장애 | R2 중지 → R0·R1만 다른 하네스 → 라우터 갱신 |
| 승인 기기 분실 | 콘솔 폐기 → 대기 승인 revoke → 새 패스키 |
| 창업자 부재 7일 | 자동 실행 중지, 서비스는 유지, 갱신·결제일 점검 |

## 6. 주간 운영 (165분)

| 분 | 일 |
|---:|---|
| 30 | SLO, 비용, 보안 경보 |
| 40 | 막힌 작업과 승인 |
| 30 | 승격 제안 최대 5건 |
| 30 | 의존성·하네스 갱신 |
| 20 | KPI와 축소 결정 |
| 15 | 피드백 대장([17](17-feedback-loop.md) §8) |

이 표는 플랫폼 관리 시간이다. 나머지 15분은 갑작스러운 일에 쓴다. 고객 문의와 사업 확인은 [14](14-business-modules.md) §7의 기업 기능 시간에 넣는다.
하네스 갱신은 자동으로 하지 않는다. W0-1 계약 시험과 대표 평가를 통과한 버전만 허용 목록에 넣는다.
