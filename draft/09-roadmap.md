# 09. 로드맵

**결론: 날짜 대신 통과 조건으로 단계를 넘긴다. 단계는 서비스 출시가 아니라 플랫폼 능력으로 나눈다.**

## 1. 산정 전제

초안 간트는 21+28+28+21=98일(14주)이다. 12주가 아니다.
가용 시간은 주 20시간이다(창업자 확정, 2026-11-25). 이 중 20%를 여유로 둔다(**제안**). 유효 시간은 주 16시간이다. 여기서 관리와 기업 기능 시간을 뺀다([14](14-business-modules.md) §7). 개발 시간은 P0·P1에서 주 15시간, P2·P3에서 주 12시간으로 잡는다.
P0·P1은 관리할 플랫폼이 아직 없어 기업 기능 1시간만 뺀다. P2부터 관리 3시간도 뺀다.
P0·P1에서는 피드백 대장 주 15분([17](17-feedback-loop.md) §8)도 뺀다. 개발 시간은 주 14.75시간이 되지만 유효 주는 바뀌지 않는다(27/14.75 → 2주, 128/14.75 → 9주).
에이전트의 병렬성은 창업자의 검토 시간을 줄이지 않는다. 아래 시간은 창업자 시간이다.

| 단계 | 시간 | 유효 주 | 결과 |
|---|---:|---:|---|
| P0 검증 | 27 | 2 | 환경 가정 확인, 자체 구현 범위 확정 |
| P1 코어·콘솔 | 128 | 9 | 안전하게 기능 3건 병합 준비, 웹에서 진행 확인 |
| P2 서비스 팩토리 | 116 | 10 | 서비스를 같은 방식으로 만들고 배포, 브랜딩·법무, 운영 대시보드 |
| P3 운영·학습 | 100 | 9 | 여러 서비스 운영, 사업 판단, 지식 이전 |
| 합계 | 371 | 30 | 플랫폼 v1 |

유효 주는 단계마다 올림했다. 2026-11-30(월)에 시작하면 30주 뒤인 2027-06-27(일)에 끝난다. 휴일은 반영하지 않았다.
Type A~D 팩과 개별 서비스의 개발 시간은 포함하지 않는다. 서비스를 시작할 때 그 서비스의 `define`에서 산정한다.
이전 추정은 255시간, 18주였다. 범위 추가로 6주, 관리·기업 기능 시간을 뺀 계산으로 5주 늘어 확정 때 29주였다. 확정 뒤 피드백 루프로 1주가 더 늘어 30주다.
추정은 실적 자료가 없는 첫 추정이다. 각 단계는 -20%에서 +60%까지 벗어날 수 있다고 본다. P1의 6개 PR 뒤 실제 시간 비율로 나머지를 다시 계산한다. 확정 때의 355시간에 구축 하네스 6시간([ADR-0012](adr/0012-build-harness.md))과 피드백 루프 8시간([ADR-0013](adr/0013-feedback-loop.md)), 하네스 보완 2차 2시간(W0-8)을 더했다. P3는 주 12시간으로 정확히 8주였으므로 4시간이 늘어 1주가 늘었다.

### 부트스트랩

AX 자체 코드는 대부분 R2다. 그러나 P1 동안에는 AX 게이트가 아직 없다.
구축 절차는 [16](16-build-harness.md)을 따른다.
1. P0과 P1은 사람이 지켜보는 일반 하네스 세션으로 개발한다. 자율 실행을 하지 않는다.
2. 수동 병합 확인표(W0-4)와 수동 이기종 리뷰를 먼저 쓴다.
3. W1-9 게이트를 통과한 커밋부터 AX가 AX를 개발한다. 이때도 감독 모드다.
4. 정책, 브로커, 실행기 변경은 그 뒤에도 항상 R2다. 이전 릴리스의 게이트가 새 릴리스를 검사한다.

## 5. 범위 조정

플랫폼의 진행과 축소는 능력과 안정성으로 판단한다. 서비스의 매출이나 수요를 기준으로 쓰지 않는다.

- 단계의 시간이 추정보다 40% 넘게 늘면 범위를 다시 정한다. 우선순위는 안전 경계, 생애주기 계약, 되돌리기, 학습, 편의 순이다. 화면이 늦어지면 사업·학습 대시보드부터 줄인다.
- 게이트를 통과하지 못하면 다음 단계의 코드를 병합하지 않는다.
- 주간 한도를 두 주 연속 소진하면 R0 작업을 멈추고 작업을 더 작게 나눈다.
- P3 전에 실제 서비스를 시작하려면 P1과 W2-1을 최소 조건으로 삼고 빠진 능력을 수동 절차로 문서화한다.
