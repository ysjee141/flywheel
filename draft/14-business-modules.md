# 14. 기업 기능 모듈

**결론: 회사가 한 번 갖추고 모든 서비스가 함께 쓰는 기능 12개를 플랫폼에 둔다. 모듈은 초안, 근거, 기록을 만든다. 결정은 창업자가 한다.**

창업자가 2026-11-25에 구성과 시간 상한을 확정했다([ADR-0010](adr/0010-business-modules.md)). 세부 값은 제안이다.

## 1. 두 종류의 모듈

| 종류 | 예 | 실행 위치 | 꺼졌을 때 |
|---|---|---|---|
| 능력 모듈 | auth, billing, telemetry, privacy | 서비스 안의 코드 | 서비스 기능이 멈춘다 |
| 기업 기능 모듈 | 브랜딩, 수익화, 법무 | AX 안의 역할, Skill, 절차, 기록 | 서비스는 계속 동작한다 |

능력 모듈 `privacy`는 내보내기와 삭제를 실행한다. 기업 기능 모듈 `legal`은 그 동작이 의무에 맞는지 검토한다.
기업 기능 모듈도 팩처럼 끼우고 뺀다. 코어는 모듈의 이름을 모른다.

## 2. 구성

각 모듈은 회사 범위와 서비스 범위를 가진다. 서비스 범위는 회사 기준을 이어받고 이유를 남겨 바꿀 수 있다.

| 묶음 | ID | 모듈 | 회사 범위 | 서비스 범위 |
|---|---|---|---|---|
| 방향 | `portfolio` | 포트폴리오 | 서비스의 시작·지속·종료, 자원 배분, 매각 준비 | 단계별 판단 자료 |
| 방향 | `validation` | 제품·시장 검증 | 조사 방법, 근거 목록 | 인터뷰, 가설·실험, 우선순위, 활성화·재방문 |
| 방향 | `founder-ops` | 창업자 운영 | 시간, 결정 기록, 주간·월간 검토 | 확인 시간 예상과 실제 |
| 시장 | `brand` | 브랜딩 | 브랜드 체계, 이름·로고 규칙, 공통 디자인 토큰 | 브랜드 정의, 로고·시그니처 시안, 리뷰 |
| 시장 | `marketing` | 마케팅 | 채널, 예산, 표현 기준, 위기 문구 | 포지셔닝, 캠페인, 동의받은 고객 목록, 성과 |
| 돈 | `monetization` | 수익화 | 전체 수익 구조, 가격 원칙, 서비스 간 잠식 | 수익 모델, 가격안, 손익 시나리오, 실험 |
| 돈 | `finance` | 재무·정산 | 현금 잔여 기간, 세금 준비금, 지원금 | 수익·비용, 환불·분쟁, 세금계산서 |
| 고객 | `support` | 고객 지원·VOC | 응대 기준, 장애 공지 문구 | 문의, 도움말, 변경 안내, 상태 페이지 |
| 고객 | `analytics` | 데이터·분석 | 공통 지표 사전, AI 품질과 비용 | 퍼널, 유지율, 실험 결과 |
| 보호 | `legal` | 법무·개인정보 | 표준 문서, 처리자 목록, 지식재산, AI 고지 | 약관·처리방침 초안, 데이터 흐름, 쟁점 |
| 보호 | `assets` | 자산·계정·계약 | 도메인, 계정, 구독, 상표, 전문가 연락처 | 서비스별 자산, 공급자 위험, 이전 가능성 |
| 보호 | `company-ops` | 회사 운영·리스크 | 의무 달력, 위험 대장, 보험, 부재·복구 계획 | 서비스별 신고와 위험 |

보안은 [06](06-quality-security.md)이 다룬다. 다시 만들지 않는다.
나중에 켜는 기능은 신뢰·안전, 현지화, 기업 영업과 견적이다. 인사와 투자 관리는 제외한다.
브랜드는 혼합 체계다. 서비스는 독립 이름을 쓴다. 회사는 보증 브랜드와 공통 디자인 기반을 제공한다.

## 3. 역할과 검토

역할은 기존 16종을 쓴다. 만든 역할은 같은 산출물을 검토하지 않는다. 코드가 계산할 수 있는 값은 모델에 맡기지 않는다.

| 모듈 | 만드는 쪽 | 검토하는 쪽 | 창업자 결정 |
|---|---|---|---|
| `portfolio` | A01 | A06 | 시작, 보류, 종료 |
| `validation` | A03 | A06 | 실험, 우선순위 |
| `founder-ops` | 코드 | 창업자 | 시간 확정, 상한 예외 |
| `brand` | A05 | A08, A07 | 브랜드 선택과 공개 |
| `marketing` | A05 | A07 | 게시, 지출 |
| `monetization` | A04 | A06, A07 | 가격 |
| `finance` | 코드 집계, A06 설명 | 대사 검사, A04 | 차이 처리, 환불 |
| `support` | A02 | A13, A07 | 발송, 환불 |
| `analytics` | A06 | 코드 검산, A01 | 지표 정의 |
| `legal` | A07, A15 | A16, 외부 전문가 | 게시 |
| `assets` | 코드, A12 | A16 | 구매, 갱신, 해지 |
| `company-ops` | A01 | A07, 외부 전문가 | 신고, 위험 수용 |

법무, 상표, 세무의 AI 결과는 쟁점 정리다. 외부 전문가의 확인일과 범위를 기록하기 전에는 확정하지 않는다.

## 4. 산출물 계약

| 산출물 | 필수 내용 | 사용하는 곳 |
|---|---|---|
| 브랜드 묶음 | 이름, 의미, 금지 사용, 로고 해시, 디자인 토큰, 유사 이름 조사 | 화면, 마케팅 |
| 주장 대장 | 문구, 근거, 확인일, 만료일, 법무 판정 | 광고, 랜딩 |
| 가격표 | 버전, 통화, 금액, 조건, 적용일, 기존 고객 처리 | billing, 약관 |
| 손익 시나리오 | 가정, 출처, 낮음·기본·높음, 민감도 | 포트폴리오 |
| 월 마감 | 수익, 비용, 차이, 세금 준비금, 원본 해시 | 대시보드 |
| 법무 묶음 | 데이터 흐름, 쟁점, 문서 버전, 전문가 확인 | release 게이트 |
| 의무 항목 | 근거, 기한, 담당, 준비물, 완료 증거 | 의무 달력 |
| 결정 기록 | 선택지, 선택, 이유, 지표 스냅샷, 다시 볼 날 | 모든 모듈 |

모듈 명세는 [스키마](schemas/business-module.schema.json)를 따른다. [예제](schemas/examples/business-modules.json)에 12개 모듈이 있다.
회사 기록은 [`company.sql`](schemas/company.sql)의 `company.db`에 둔다. `state.db`와 나눈다. 기록은 고치지 않고 새 버전을 더한다.

## 5. 생애주기 연결

| 상태 | 필요한 모듈 산출물 |
|---|---|
| `discover` | 문제 근거, 수익화 가설, 포트폴리오 판단 |
| `define` | 브랜드 묶음, 가격 가설, 법무 묶음 초안, 지표 정의 |
| `build` | 디자인 토큰 적용, 동의·약관 반영, 지표 수집 |
| `release` | 주장 대장, 가격표, 법무 확인, 자산 점검, 지원 준비 |
| `operate` | 월 마감, 지원·마케팅 성과, 실험, 의무 달력 |
| `retire` | 고지, 환불, 데이터 삭제, 계약·자산 해지 |

매니페스트의 적용 여부에 따라 필요 없는 산출물은 `not_applicable`과 이유로 남긴다. 예를 들어 무료 내부 도구에는 가격표가 없다.

## 6. 데이터와 안전

- 회사 기록은 기본적으로 `confidential`이다. 에이전트는 게이트웨이로 허용된 필드만 읽는다.
- 은행·결제 원본은 로컬 코드가 읽는다. 모델에는 필요한 집계만 보낸다. 주민등록번호와 계좌번호는 보내지 않는다.
- 재무 자료는 처음에 수동 입력과 파일 가져오기를 쓴다. 파일 해시와 행 수를 기록하고 합계를 대사한다.
- 웹 조사와 고객 문의를 읽은 작업은 `tainted`다. 그 작업은 재무 기록을 읽지 못한다.
- 마케팅은 동의 근거, 시각, 철회가 없는 수신자를 거부한다.
- 외부에 영향을 주는 작업은 [04](04-hooks-policy-hitl.md) §5의 승인을 거친다.
- 장기 부재 계획의 복구 키는 저장소에 두지 않는다. 오프라인 위치의 이름만 기록한다.

## 7. 창업자 시간

창업자 시간은 확인과 결정에 직접 쓴 시간이다. AI 실행 시간이 아니다.

| 구분 | 출시 전 | 출시 후 |
|---|---:|---:|
| 기업 기능 상한 (주) | 1시간 | 3시간 |
| 플랫폼 관리 상한 (주) | 3시간 | 3시간 |
| 여유 (주) | 4시간 | 4시간 |
| 개발·개선에 남는 시간 (주, 최소) | 12시간 | 10시간 |

숫자는 임시값이다. 4주의 기록으로 다시 정한다. 관리와 기업 기능은 유효 시간 16시간 안에서 쓴다.

1. 작업을 만들 때 예상 확인 시간을 분으로 적는다.
2. 사고, 보안, 기한, 환불을 먼저 넣는다. 나머지는 남은 시간 안에서 순서대로 넣는다.
3. AX는 화면 사용으로 시간 초안만 만든다. 창업자가 확정한 값만 합계에 쓴다.
4. 매주 5분 안에 확정하고 다음 주를 조정한다.

| 상황 | 동작 |
|---|---|
| 80% | 알림 |
| 100% | 급하지 않은 새 확인 요청을 다음 주로 옮김 |
| 1주 초과 | 원인을 주간 검토에 표시 |
| 2주 연속 초과 | 새 서비스의 `build` 진입 보류 |

상한은 일의 양과 순서만 정한다. 위험 등급, 리뷰, 승인을 낮추지 않는다.
시작한 작업, 사고, 보안, 법적 기한, 환불, 운영 중인 서비스는 멈추지 않는다. 창업자는 이유를 남기고 상한을 넘길 수 있다.

## 8. 만드는 시점

| 시점 | 범위 |
|---|---|
| P1 | 승인 종류의 스키마 |
| P2 | 기능 팩 형식, `company.db`, 시간·결정 기록, 브랜딩·법무 최소판 |
| P3 | 수익화·재무, 포트폴리오·회사 운영·자산 최소판. 모의 데이터로 검증 |
| 첫 서비스 | 제품·시장 검증, 마케팅, 지원, 분석의 실제 연결 |

## 9. 수용 기준

- B-01: 시험용 열셋째 모듈을 코어 변경 없이 추가하고 제거한다.
- B-02: 만든 역할이 자기 산출물을 검토하면 거부한다.
- B-03: 필수 모듈 산출물이 없으면 생애주기 전이를 거부한다. `not_applicable`에는 이유가 필요하다.
- B-04: 모의 재무 파일의 중복, 누락, 합계 차이를 찾는다.
- B-05: 동의가 없거나 철회한 수신자는 발송 승인 요청에 들어가지 않는다.
- B-06: 시간 상한을 넘어도 위험 등급과 필수 리뷰가 바뀌지 않는다.
- B-07: `tainted` 작업의 재무 기록 읽기를 거부한다.
- B-08: 회사 기록의 덮어쓰기와 삭제를 DB가 거부한다.
